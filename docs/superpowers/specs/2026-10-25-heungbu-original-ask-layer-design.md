## 2. 목표 / 비목표 / 실패 조건

목표
1. 흥부와 놀부 시나리오(`src/data/heungbu.json`)가 원작 흥부전의 사건을 모두 담는다. 특히 놀부가 제비를 일부러 다치게 해 박씨를 받고 박에서 벌을 받는 짝 구조를 순한 표현으로 복원한다(2026-10-22 보류 결정의 실행).
2. 아이가 어떤 선택을 해도 원작 사건은 전부 일어난다. "다른 결말" 조건은 쓰지 않는다.
3. 세 선택 지점 각각 **직전**에 묻기 층이 있다. 아이가 인물을 고르고 질문 카드를 고르면 인물이 목소리로 대답하고, 대답에 따라 단서 그림이 바뀔 수 있다. 질문은 지점당 최대 2개, 언제든 건너뛸 수 있다.
4. 그중 두 지점(c1 제비, c3 놀부)에서 마이크 버튼으로 **말로 물을 수 있다.** 브라우저 음성 인식(Web Speech API)으로 받은 글을 미리 쓴 질문에 키워드로 맞추고, 맞으면 그 질문을 한 것으로 처리한다. 대답을 고르는 부분은 나중에 LLM으로 갈아 끼울 수 있게 경계를 둔다.
5. 아이가 무엇을 물었는지(카드/음성, 음성이면 인식된 글)가 로그에 남고, 부모 리포트의 첫 단락 "오늘 궁금해한 것"이 된다.
6. 기존 테스트가 모두 통과하고, 개미와 베짱이는 바뀐 스키마에서도 그대로 검증·실행된다.

비목표
- 개미와 베짱이의 원작 복원·묻기 층(다음 작업).
- 묻기 대답에 LLM을 붙이는 것(경계만 만든다).
- 물건을 건드려 살피는 핫스팟(인물에게 묻기만).
- 아이 음성 녹음·저장(인식된 글만 남긴다).
- CSV 열 추가(27열 유지), 리포트 화면의 시각 개편, 새 디자인.

실패 조건(만들어도 실패)
- 아이가 묻기 화면에 갇혀 이야기 흐름이 길게 멈춤. 묻기는 건너뛸 수 있어야 하고 자동 진행 타이머나 강제 질문이 없어야 한다.
- 인식 실패를 아이 탓으로 남김. 인식 실패는 "아이의 이해 부족"으로 리포트에 쓰지 않는다.

## 4. 이야기

### 4.1 새 척추

```
p1  옛날 형제 소개 → 처마 밑 다친 제비 발견 (기존 유지)
c1  흥부는 어떻게 할까? (c1a 돌봐 준다[원작] / c1b 그냥 지나간다)
p2  이듬해 봄, 제비가 돌아와 박씨를 떨어뜨림 (수정: "주웠어요"가 아니라 제비가 물어온 것임을 명시)
c2  흥부는 어떻게 할까? (c2a 마당에 심는다[원작] / c2b 그릇에 넣어 둔다)
pN  [새 장면] 놀부가 소문을 듣고 흉내 냄 → 제비를 일부러 다치게 함 → 놀부 박에서 벌 → 집과 곡식을 잃음
p3  눈 오는 밤 놀부가 문을 두드림 (수정: "욕심을 부리다가 모두 잃었어요" 문장을 pN을 받는 문장으로 교체)
c3  흥부는 어떻게 할까? (c3a 들인다[원작] / c3b 문을 열지 않는다 / c3c 먹을 것만 건넨다)
p4  봄 (기존 유지)
end 결말 (endings.original 유지)
```

새 장면의 id는 빌더가 정하되(제안: `p2n`), 기존 passage id는 바꾸지 않는다. 검증기는 passage id에 순번 규칙을 강제하지 않는다.

### 4.2 작성 규칙 개정 — 원작 사건은 모든 경로에서 일어난다

기존 R8("척추는 직전 선택 결과를 전제하지 않는다")은 다른 결말을 허용하기 위한 규칙이었다. 1A에서는 척추가 원작 사건을 전제해도 된다. 대신 **원작과 다른 선택의 모든 경로는 척추로 돌아오기 전에 원작 사건을 성립시켜야 한다.**

- `rewind`(되돌리기): 기존 그대로. 짧은 결과 → "만약 ~했다면" 대비 → 다시 고르기 → 원작 결과. 3회째는 원작으로 강제.
- `converge`(원작 수렴) — **흐름을 바꾼다(2026-10-25 검토 뒤 확정)**: `consequence`(아이 선택의 짧은 결과) → `bridge`(**흥부가 자기 이유를 말하고 마음을 바꿔 원작 행동으로 돌아섬**, 2~3문장) → **원작 선택지의 `consequence`를 그대로 이어 읽음** → 척추. 되돌리기가 재선택 뒤 원작 결과로 돌아가는 것과 같은 구조이며, 두 조건의 차이는 "아이가 다시 고르느냐(되돌리기) / 흥부가 스스로 마음을 바꾸느냐(수렴)"뿐이다.
  - 이렇게 하면 다리글이 다음 척추의 전제를 직접 서술할 필요가 없고(원작 결과가 서술한다), 좋은 결과는 모든 경로에서 전부 읽히며("좋은 결과가 나쁜 결과보다 길다" 유지), 원작 결과를 베껴 쓰는 일도 없다.
  - 다리글은 **원작 행동을 시작하는 순간**에서 끝난다. c1b 예: 흥부가 빗자루를 다시 들었지만 '찌르르' 소리가 자꾸 마음에 걸림 → "그래도 다리가 아픈 걸 그냥 둘 수는 없어" → 처마 밑으로 되돌아가 제비를 두 손으로 감싸 안음(→ c1a consequence "흥부는 제비를 집으로 데려왔어요…"로 이어짐). c2b 예: 그릇 속 박씨를 들여다보다 "제비가 멀리서 물어다 준 건데, 흙에 심어야 싹이 나지" → 박씨를 들고 마당으로 나감(→ c2a consequence "흥부는 손가락으로 땅을 콕콕 파고…"). c3b·c3c는 현재 다리글이 이미 이 꼴이라("형님, 우리 집으로 가요") 끝 문장만 c3a consequence와 겹치지 않게 다듬는다.
  - 기존 c1b·c2b 다리글(제비가 사라짐 / 내년에 심기로 함)은 폐기한다. 다리글 문단 수가 바뀌면 `art.pages`의 해당 키 배열 길이를 맞춘다(그림은 재사용하거나 비운다; 새로 그릴 필요 없음).
  - 아이의 제안은 틀렸다고 말하지 않는다. 흥부의 마음을 알게 된 것으로 남긴다. 다리글에 "다시 골라", "틀렸어" 금지(기존 규칙).
  - 엔진 변경: converge 경로의 `bridge` 마지막 페이지 뒤에 같은 선택 지점의 원작 선택지 `consequence`를 노드 id `c1.c1a.consequence`로 읽고 척추로 간다. 대본 생성기·분량 표·`art.ts`의 재사용 규칙(bridge는 consequence 그림 차용)은 그대로 성립한다.
- `altEnding`(다른 결말): 쓰지 않는다. 5절 참고.

따라서 **모든 경로가 원작 선택지의 consequence를 읽는다**(원작 선택·되돌리기·수렴·분기 off 모두). 척추는 그 내용을 전제해도 된다. R8은 "척추 passage는 원작 선택지 consequence까지의 사건을 전제할 수 있다. 다른 선택의 consequence·bridge 내용은 전제하지 않는다"로 바꿔 계획서·각색점검표에 적는다. "이해 질문의 정답 사실은 척추 passage 안에만"(R5)은 유지한다.

### 4.3 새 장면 pN — 놀부

내용 요건
- 흥부네 박 소문 → 놀부가 흥부에게 사연을 물음 → 집에 와서 제비를 **일부러** 다치게 하고 헝겊을 감아 줌 → 제비가 날아갔다가 박씨를 떨어뜨림 → 놀부가 심고 기다림 → 박을 가르니 보물 대신 **먹구름과 세찬 바람**이 쏟아져 곡식·비단옷·큰 집을 휩쓸어 감 → 놀부가 빈 마당에 홀로 남음.
- 가해는 **한 문장**, 상처 묘사 없음("일부러 다리를 아프게 했어요" 수준). 도깨비·매질·오물 없음. 벌은 날씨 현상으로. 죽음·피 없음.
- 놀부를 외모·성격으로 비하하지 않는다. 행동(욕심내어 흉내 냄)만 서술한다.
- 분량: 문단 **6~7개**(= 페이지 6~7장), 공백 제외 **300자 이하**. 비교 기준은 흥부가 받은 좋은 결과 전체(c1a consequence 263자 + c2a consequence 237자 = 500자)이며 pN은 그 절반을 넘지 않는다. 이 원칙(Lee 2014: 나쁜 결과는 짧게, 좋은 결과는 길고 분명하게)은 아이 선택의 결과뿐 아니라 척추의 놀부 벌에도 적용한다. 각색점검표의 "좋은 결과가 나쁜 결과보다 길다" 항목에 pN 행을 추가한다.
- 시간 순서: 흥부 박(가을) → 소문 → 이듬해 봄 놀부의 제비 → 그해 가을 놀부 박 → 그해 겨울(p3). p3 첫 문장 "그해 겨울"이 이어지도록 pN의 마지막이 가을에 끝난다.

초안(7문단, 공백 제외 약 290자. 빌더가 다듬되 300자를 넘기지 않는다. 문장은 전부 새로 쓴 것이며 기존 판본 복제가 아님):
1. 흥부네 박 이야기는 금세 온 마을에 퍼졌어요. 소문을 들은 놀부가 흥부에게 달려와 물었어요. "그 보물은 다 어디서 났느냐?"
2. 흥부는 다친 제비를 돌봐 준 일과 박씨 이야기를 숨김없이 들려주었어요.
3. 집에 돌아온 놀부는 처마 밑 제비 둥지를 올려다보았어요. '나도 제비만 있으면 되겠구나.'
4. 놀부는 둥지에서 제비 한 마리를 꺼내 일부러 다리를 아프게 했어요. 그러고는 "내가 고쳐 줄게" 하며 헝겊을 둘둘 감았어요.
5. 이듬해 봄, 그 제비가 놀부네 마당에 박씨 하나를 떨어뜨렸어요. 놀부는 박씨를 심고 날마다 지붕만 올려다보았어요.
6. 가을에 놀부가 톱으로 박을 가르자, 쌀도 보물도 나오지 않았어요. 박 속에서 시커먼 먹구름과 세찬 바람이 쏟아져 나왔어요.
7. 바람은 놀부네 곡식도, 비단옷도, 큰 집도 모두 휩쓸어 가 버렸어요. 놀부는 텅 빈 마당에 혼자 남았어요.

### 4.4 그 밖의 글 수정

- p2: 제비 귀환은 c1a consequence 마지막 두 페이지("다음 해 봄, 그 제비가 다시 돌아왔어요 / 발 앞에 무언가를 톡 떨어뜨리고")가 이미 서술하고, 4.2에 따라 모든 경로가 그것을 읽는다. 그러므로 p2는 사건을 다시 말하지 않고 **받기만** 한다: "박씨를 주웠어요" → "제비가 떨어뜨린 것은 작고 동그란 박씨였어요" 정도의 최소 수정. "빈 땅·빈 그릇" 단서 문장은 유지한다(c2 보기의 근거). 문단 수는 유지해 `art.pages.p2`를 건드리지 않는다.
- p3: 둘째 문장을 pN을 받는 문장으로("놀부네 집은 바람에 휩쓸려 사라지고, 곡식도 남지 않았어요" 같은 1~2문장). 문단 수가 바뀌면 `art.pages.p3` 배열 길이를 맞춘다(R9).
- 이해 질문: 4~5개 유지. 최소 1개는 pN을 가리킨다(예: inference "놀부는 왜 제비 다리를 아프게 했을까?" → "박씨를 받고 싶어서", answerFact는 pN 문장 그대로). 어느 질문을 빼거나 바꿀지는 빌더가 정한다.
- parentPrompts: 놀부 장면이나 묻기와 이어지는 열린 질문 1개 추가(총 3개 이상 유지).
- 분량(AC-4): 원작 경로(척추 + 원작 consequence + 결말) 공백 제외 **1,900자 이하**(약 7분). 현재 1,474자 + pN 약 290자 + p2·p3 수정분으로 1,800자 안팎이 예상되므로 다른 본문을 늘리지 않는다. 묻기 대답은 선택 사항이라 분량 계산에 넣지 않되, 전부 2개씩 물었을 때 +300자를 넘지 않게 대답을 짧게 쓴다. 되돌리기 최장 경로 상한은 2,200 → **2,400자**로 올린다(되돌리기는 이제 기본값이 아닌 실험 토글이므로. 내 결정).
- 각색점검표를 갱신한다: 새 장면 항목(가해 한 문장, 그림은 놀부가 제비를 손에 든 모습까지만), 개정 R8, 분량 표, 묻기 대답 금지어 검사.

## 5. 다른 결말 끄기와 기본 조건

- 실험자 화면의 "다른 선택 처리" 목록에서 `altEnding`을 뺀다. `VALID_CONDITIONS`는 7 → 5(off, rewind-why, rewind-nowhy, converge-why, converge-nowhy). 대본 생성기·테스트의 조합 수를 맞춘다.
- `DEFAULT_SETTINGS.defaultConditions`를 `{ branching: true, mismatch: "converge", askWhy: true }`로.
- 타입 `MismatchKind`, 스키마의 `mismatch.altEnding` 필수 조건, 엔진의 altEnding 경로, heungbu.json의 altEnding 본문과 `art.pages`의 altEnding 키는 **그대로 둔다**(개미 JSON과 기존 로그·테스트 호환, 도달 불가). 정리는 다음 작업. 내 결정이며, 빌더가 스키마에서 선택 항목으로 바꾸는 쪽이 더 싸다고 판단하면 그렇게 해도 된다. 단 ant.json은 수정 없이 통과해야 한다.
- 리포트 템플릿·LLM 프롬프트에서 다른 결말을 전제한 문장이 있으면 지운다.

## 6. 묻기 층

### 6.1 아이가 겪는 흐름

1. 선택 지점 직전 passage의 마지막 페이지를 다 들으면 **묻기 화면**으로 간다(기존에는 바로 선택 화면). 그림은 직전 페이지 그림을 유지한다.
2. 화면 아래에 인물 버튼 1~2개(예: 제비, 흥부)가 있고, 진입 시 짧은 안내를 1회 낭독한다(예: "제비한테 물어볼까?"). 오른쪽 아래 책장 귀퉁이(기존 next)로 언제든 선택 화면으로 넘어갈 수 있다. 음성이 켜진 지점이면 마이크 버튼도 함께 보인다.
3. 인물을 누르면 그 인물의 **질문 카드 2~3개**가 보기 목록(기존 `.options` 스타일)으로 뜬다. 카드는 한 번 누르면 읽어 주고(listen), 같은 카드를 다시 누르거나 "이걸로 할래"로 확정한다(기존 confirmMode 규칙 그대로).
4. 확정하면 **대답 화면**(본문 화면과 같은 페이지 형식, 문단 1~2개)에서 인물의 대답을 낭독한다. 질문에 `clue` 그림이 있으면 그 그림으로 바뀌고, 없으면 그림을 유지한다. 대답이 끝나면 다음 → 묻기 화면으로 돌아온다(남은 질문 수가 있으면). 이미 한 질문의 카드는 흐리게 표시하고 다시 고를 수 없다.
5. 질문 2개를 다 쓰면 안내 없이 선택 화면으로 간다. 묻기 화면에서 넘어가면 선택 화면으로 간다.
6. 선택 화면 이후는 기존과 같다. 되돌리기로 다시 고를 때(attempt 2 이상) 묻기 화면은 다시 나오지 않는다.
7. 분기 off 조건에서도 묻기 화면은 나온다(묻기는 선택과 독립된 층). 설정 `askLayer`가 꺼져 있으면 묻기 화면 자체가 없다(기존 흐름).

### 6.2 음성(2B)

- 조건: 그 선택 지점의 `ask.voice === true` 이고, 설정 `voiceAsk`가 켜져 있고, 브라우저가 `SpeechRecognition`/`webkitSpeechRecognition`을 제공할 때만 마이크 버튼을 보인다. 아니면 버튼 없음(오류 표시 없음).
- 누르면 인식을 시작한다(`lang: "ko-KR"`, `interimResults: false`, `maxAlternatives: 3`, 1회 결과). 듣는 중임을 버튼 상태로 보여 주고, 6초 안에 결과가 없으면 멈춘다. 인식 중에는 TTS를 멈춘다.
- 인물을 고르기 전에도 누를 수 있다. 이때는 그 지점의 모든 인물의 질문을 대상으로 맞춘다("제비야 왜 못 날아?" 한 번에). 인물을 고른 뒤에는 그 인물의 질문만 대상으로 한다.
- 맞으면: 그 질문을 카드로 확정한 것과 같은 흐름(대답 화면). 로그에 `via: "voice"`와 인식된 글이 남는다. 남은 질문 수가 1 줄어든다.
- **이미 한 질문**에 맞으면(아이가 같은 말을 다시 하는 경우): 인식 실패로 세지 않고 `voiceFails`도 올리지 않는다. 그 대답을 다시 들려주되(대답 화면) 남은 질문 수는 줄이지 않는다. 로그는 `ask_repeat`(question_id, detail `{via:"voice", transcript}`)로 남기고 `ask_confirm`은 찍지 않는다. 리포트에는 한 번만 나온다. 매처는 `asked` 목록을 **받지 않는다**(이미 한 질문도 정상 후보). 반복 여부 판단은 엔진이 한다.
- 못 맞추면: 인물의 `unmatched` 문장을 낭독한다(예: "음… 찌르르. 무슨 말인지 잘 모르겠어. 다시 말해 줄래?"). 남은 질문 수는 줄지 않는다. 같은 지점에서 두 번째로 못 맞추면 `unmatchedFinal`을 낭독하고("대신 이 중에서 골라 줄래?") 그 지점에서는 마이크 버튼을 숨긴다. 카드는 계속 쓸 수 있다.
- 권한 거부·네트워크 오류·no-speech 등 인식 자체의 실패는 못 맞춘 것과 같이 처리하되 로그 `voice_fail`에 이유를 남긴다.
- 음성은 저장하지 않는다. 남는 것은 인식 결과 글(대안 최대 3개)뿐이다. Chrome의 Web Speech는 음성을 구글 서버로 보내므로 실험 동의서에 적어야 한다(동의서는 이 작업 범위 밖, 메모만).

### 6.3 대답 고르기의 경계(나중에 LLM으로 교체)

```ts
// src/ask/responder.ts
export interface AskInput { storyId: string; choicePointId: string; characterId: string | null; transcript: string; alternatives: string[] }
export interface AskOutput { characterId: string; questionId: string; answerText: string[] } // null이면 못 맞춤
export interface AskResponder { respond(input: AskInput, ask: AskBlock): Promise<AskOutput | null> }
```

- 기본 구현 `KeywordResponder`: 순수 함수 `matchQuestion(transcript, alternatives, characters, selectedCharacterId)`를 감싼다. 정규화(공백·문장부호 제거, 소문자) 후 각 질문의 `keywords`가 부분 문자열로 들어 있는 개수를 점수로, 인물 이름이 들어 있으면 그 인물의 질문에 +2. 점수 1 이상 중 최고점, 동점이면 JSON 순서가 앞선 것. 대안 3개 중 가장 높은 점수를 쓴다. 결정적이어야 하고 테스트로 고정한다.
- 러너는 `respond`의 결과를 `voiceResult` Action으로 엔진에 넣는다. 엔진은 브라우저 API나 비동기를 모른다. 나중에 `LlmResponder`를 끼우면 `answerText`가 자유 문장이 될 수 있으므로 엔진의 대답 화면은 `answerText`를 그대로 낭독한다(질문 id로 다시 찾지 않는다).

### 6.4 데이터(JSON) — 선택 지점에 `ask` 블록 추가(선택 사항)

  "ask": {

- 질문 글: 아이가 할 법한 말투(반말, 짧게). 대답: 인물 1인칭, 1~2문장, 공백 제외 40자 이내 권장, 다음 선택의 **단서**가 되게(제비: 다리가 아프다·혼자다 / 박씨: 제비가 멀리서 물어왔다·흙에 심어야 싹이 난다 / 놀부: 춥다·잘 곳이 없다·미안하다). 대답이 정답을 지시하지 않게("돌봐 줘"라고 말하지 않는다).

### 6.5 엔진 변경

- `Screen`에 `"ask"` 추가, `BodyScreen`에 `"askAnswer"` 추가.
- `AskView { screen: "ask"; nodeId; choicePointId; characters: {id,name,portrait?}[]; selectedCharacterId: string|null; questions: {id,text,asked:boolean}[] (선택한 인물의 것, 없으면 []); selectedQuestionId: string|null (listen으로 강조된 것); asksLeft: number; voice: "hidden"|"idle"|"listening"; voiceFails: number }`
- Action 추가: `askCharacter {characterId}`, `askSkip`, `voiceStart`, `voiceResult {transcript, alternatives, matched: {characterId, questionId, answerText}|null}`, `voiceFail {reason}`. 카드의 듣기·확정은 기존 `listen`/`confirm` 재사용(화면이 ask일 때 optionId = `<characterId>.<questionId>`).
- 상태: 지점별 `asked: string[]`, `voiceFails: number`. 세션 직렬화 가능 유지.
- 묻기 화면 진입은 "선택 지점 직전 passage의 마지막 페이지 ttsDone 후 next" 시점. `askLayer` 설정이 꺼져 있거나 그 지점에 `ask`가 없으면 기존처럼 선택(또는 분기 off의 offNarration)으로.
- 대답 화면은 본문 화면 규칙(페이지 자동 낭독 → next)을 따르고, 끝나면 `asksLeft > 0`이면 묻기 화면, 아니면 선택 화면.
- `EngineSettings`에 `askLayer: boolean` 추가(기본 true). 음성 가능 여부는 러너가 `init` 때 `voiceAvailable: boolean`으로 넘긴다.

### 6.6 UI

- 인물 버튼은 **그림 밖**의 보기 버튼이다. 그림 위를 눌러 반응하는 핫스팟은 여전히 금지(README 금지 사항·교육근거조사 3.3). README 금지 사항에 "인물 버튼(그림 밖)은 허용, 그림 위 핫스팟은 금지"로 구분을 적는다. README의 그림 파일 확장자 표기(.png)도 실제(.webp)로 고친다.
- 기존 아이 화면(`src/ui/child.ts`) 스타일과 책장 넘기기 규칙을 그대로 쓴다. 인물 버튼은 그림 아래 보기 목록 자리에 가로로 놓고, 초상 그림이 있으면 둥근 그림 + 이름, 없으면 이름만. 마이크 버튼은 같은 줄 오른쪽, 듣는 중에는 테두리가 천천히 커졌다 작아지는 정도의 표시(효과음·별 없음).
- 문구(`strings.ts`): `askIntroDefault: "물어보고 싶은 게 있어?"`, `askSkip`은 버튼 없이 책장 귀퉁이로, `micLabel: "말로 물어볼래"`, `listening: "듣고 있어"`.
- 실험자 화면(`experimenter.ts`): 토글 2개 추가 — "묻기 층"(`askLayer`, 기본 켬), "음성 질문"(`voiceAsk`, 기본 켬). 설정(`Settings`)과 `SessionMeta`에 같은 이름으로 저장. **`voice`라는 이름은 쓰지 않는다** — `SessionMeta.voice`와 `session_start.detail.voice`는 이미 TTS 음성 이름이며 그대로 둔다. 조건 목록에서 altEnding 제거(5절).
- 음성 인식 모듈 `src/asr.ts`: `createAsr({lang, onResult, onError})`로 감싸고 `isAsrSupported()` 제공. 테스트는 TTS처럼 의존성 주입(가짜 Recognition)으로.

## 7. 로그

CSV 27열 그대로. `EventType`에 추가:
- `ask_character` (node_id `c1.ask`, option_id = characterId)
- `ask_listen` (question_id = `c1.ask.swallow.q1`)
- `ask_confirm` (question_id, detail `{ via: "card" | "voice", transcript?: string }`, rt_ms = 묻기 화면 진입(또는 직전 대답 끝) → 확정)
- `ask_skip` (detail `{ asked: n }`)
- `ask_repeat` (question_id, detail `{ via: "voice", transcript }`) — 이미 한 질문을 말로 다시 한 경우
- `voice_start`, `voice_result` (detail `{ transcript, alternatives, matched: "c1.ask.swallow.q1" | null }`), `voice_fail` (detail `{ reason }`)
- `session_start`의 detail에 `{ askLayer, voiceAsk, asr: "available" | "unsupported" }` 추가(기존 `voice`(TTS 음성 이름)·`pictures`는 유지).

`screen_enter`·`tts_*`·`next_click`은 새 화면에서도 기존 규칙대로 찍힌다. 감사(`audit.ts`)·CSV 테스트에 새 이벤트를 넣는다. 인식 글은 아이의 발화이므로 내보내기 파일에 포함되며, 참가자 코드 외 식별 정보는 없다(기존 AC-16 원칙).

## 8. 부모 리포트(3A)

- `ReportInput`에 `asks: { scene: string; character: string; question: string; via: "card" | "voice" }[]` 추가. `scene`은 선택 지점의 짧은 장면 이름(JSON `ask.sceneLabel`, 예: "다친 제비를 본 장면"; 없으면 prompt).
- 음성으로 맞았을 때의 인식 글(`said`)은 **LLM 요청에 보내지 않는다.** 아이의 자유 발화에는 이름 등이 섞일 수 있다(AC-16의 취지). `summarize`는 `ReportInput`과 별도로 `saidByAsk: (string | undefined)[]`를 돌려주고, 템플릿 리포트만 이것을 인용한다. LLM 결과를 쓸 때는 `curiosity` 뒤에 템플릿이 만든 인용 문장을 덧붙이지 않는다(단순화; 인용은 템플릿 경로에서만). `buildRequest` 테스트(AC-16)에 "요청 본문에 `said`·인식 글이 없음"을 추가한다.
- `ReportText`에 `curiosity: string` 추가. 리포트 화면의 **첫 단락** "오늘 궁금해한 것"으로 보여 준다. 그다음 기존 선택 요약·이해 질문·'오늘 이렇게 물어보세요' 순.
- 템플릿: 없으면 "오늘은 인물에게 따로 물어보지 않고 이야기를 끝까지 들었어요."(중립). 있으면 장면별로 "다친 제비를 본 장면에서 제비에게 「왜 못 날아?」 하고 물어봤어요." 음성이면 "직접 말로 「제비야 왜 못 날아」라고 물었어요."를 덧붙인다. 묻기와 이어서 고른 선택·이유가 있으면 한 문장으로 잇는다("그다음 「다친 제비를 돌봐 준다」 쪽을 골랐고, 이유로 「제비가 아파 보여서」를 꼽았어요").
- 못 맞춘 음성 시도는 리포트에 쓰지 않는다. 아이의 이해에 대한 판단으로 바꾸지 않는다.
- LLM 프롬프트: `curiosity` 필드와 위 규칙을 추가한다. 금지어 필터·숫자 금지·AC-16(참가자 코드 없음) 유지. 파서는 `curiosity`가 없으면 템플릿으로 대체(`parse_error`).

## 12. 내가 정한 것(사용자 확인용)

검토(빌더 체크) 뒤 사용자가 확정한 것: 수렴 경로가 다리글 뒤 원작 consequence를 이어 읽는다(4.2). 시간은 충분하다고 했으므로 13절은 우선순위가 아니라 작업 순서다.

검토 뒤 내가 정한 것:
- pN 300자 이하·6~7페이지, 비교 기준은 c1a+c2a(500자).
- 음성 토글 이름 `voiceAsk`(`voice`는 TTS 음성 이름으로 이미 사용 중).
- 이미 한 질문을 다시 말하면 실패로 세지 않고 대답을 다시 들려줌(`ask_repeat`).
- 인식 글은 LLM에 보내지 않고 템플릿 리포트에서만 인용.

처음부터 정한 것:
- 기본 조건 `converge`, 되돌리기는 토글, 다른 결말은 UI에서만 제거.
- 묻기는 인물에게만(핫스팟 없음), 지점당 최대 2개, 음성은 c1·c3만.
- 음성은 브라우저 내장 인식 + 키워드 매칭, 음성 저장 없음, 못 맞추면 2회까지.
- 놀부 박의 벌은 먹구름과 바람, 가해는 한 문장.
- 되돌리기 최장 경로 상한 2,400자.
- 리포트 첫 단락을 "오늘 궁금해한 것"으로.
- 개미와 베짱이는 이번에 손대지 않음.
